# 生成提交信息

只根据当前仓库的真实差异生成建议提交信息。即使用户通过本 Skill 表达“提交”，本 Skill
也只负责生成文本；实际提交必须由独立、明确的用户操作指令处理。

## 输入

使用以下事实：

- 当前仓库状态；
- staged 或 working tree 的真实 diff；
- 当前会话中实际运行过的诊断、测试和验证命令及结果；
- 必要时读取的未跟踪文件内容；
- 用户已明确提供且与 diff 一致的动机或问题背景。

原始任务描述可以解释目标，但不能证明某项实现、根因、影响或验证已经发生。

## Git 行为边界

无条件遵守：

- 不执行 `git add`；
- 不执行 `git commit`；
- 不执行 `git push`；
- 不创建、切换、重命名或修改分支；
- 不修改工作区文件；
- 不为了补充提交说明而运行测试、构建或其他实现验证；
- 只输出建议提交信息。

## 差异调查

按顺序检查：

```text
git status --short
git diff --cached --name-status
git diff --cached
git diff --name-status
git diff
```

必要时读取 `git status --short` 中的未跟踪文件，但不要自动把它们纳入范围。

应用以下规则：

1. staged 有内容时，只根据 staged diff 生成，不混入 unstaged 或 untracked 内容。
2. staged 为空时，根据 working tree 生成，并明确说明依据是未暂存改动。
3. staged 和 working tree 都为空时，说明没有可用于生成提交信息的变更。
4. 识别新增、删除、重命名、生成文件、文档和测试，不只依赖文件名或 diff stat。
5. 只有部分文件已暂存时，明确忽略其余 working-tree 修改。
6. 不把无关用户改动、临时文件或未纳入所选范围的文件写进提交信息。
7. 生成文件如果真实存在于所选 diff 中，按其实际作用描述，不能一概忽略。
8. 只描述相对父提交的最终差异，不描述已撤销的中间尝试、失败过程或未来计划。

## 混合主题检查

判断所选范围是否包含多个可以独立提交的无关主题。

如果存在混合主题：

- 先说明建议拆分的主题和对应文件；
- 不强行包装成一个模糊主题；
- 只有在边界清楚时，才分别给出候选提交信息；
- 不为拆分而执行暂存或其他 Git 操作。

## 提交类型与标题格式

使用：

```text
<type>(<scope>): <subject>
```

支持的 type：

- `feat`：增加用户或开发者可用能力；
- `fix`：修复已存在的错误行为；
- `refactor`：保持外部行为的结构调整；
- `test`：只增加或调整测试；
- `docs`：只修改文档；
- `chore`：工具、配置、维护或其他不属于以上类型的变更。

scope 可选，使用主要模块名称。变更横跨多个模块且没有清晰主模块时省略 scope。

标题必须：

- 使用英文和 ASCII 字符；
- 使用祈使语气，例如 `add`、`fix`、`refine`，不要使用过去式、进行时或完成时；
- 保持单行，subject 首字母使用小写，专有名词按规范大小写；
- 目标控制在 50 个 ASCII 字符以内，整行不得超过 65 个 ASCII 字符；
- 清晰描述本次最终差异，避免 `fix bugs`、`update files`、`modify modules` 等模糊表述；
- 避免 `implement the feature of`、`fix the bug of` 等可以删减的冗余措辞。

判断标题是否过于模糊时，检查它能否不加修改地用于许多其他提交；如果可以，应继续具体化。

## 提交说明的内容

默认生成标题和正文概述。只有当所选 diff 很小、单一且标题已经完整表达修改时，才可以
只输出标题。中大型修改必须包含正文，正文首段必须是变更概述。

### 变更概述

- 用中文概要说明实现了什么、解决了什么，以及必要的意图或动机。
- 与所选 diff 完全匹配，不遗漏主要修改，也不扩大范围。
- 放在正文首段，一般为 1～2 行，不超过 3 行。

### 问题描述

Bug 修复在证据充分时说明：

- 用户或系统可见的原始现象；
- 已确认的触发条件或复现方法；
- 已确认的发生频率；
- 已确认的影响、范围和程度；
- 黑盒可见影响，而不只是内部实现现象。

如果当前 diff、诊断记录或用户提供的事实不能证明频率、复现步骤或影响范围，就省略这些
细节，不能为了让正文完整而猜测。

### 原因分析

- 说明由代码、诊断或已确认事实支持的直接原因和根本原因。
- 从机制上解释为什么会出现问题，以及旧实现在哪个边界失效。
- 不把修改方案反推成未经证明的根因。

### 修改方案

- Feature 说明新增或调整了什么能力，以及主要实现结构。
- Bug 说明如何修复原因，而不只是列出改过的文件。
- Refactor 说明结构如何变化，以及哪些外部行为保持不变。
- 必要时说明事实源、事务、平台边界或兼容性处理。

对于 Bug，优先形成“问题描述 → 原因分析 → 修改方案”的完整逻辑链；任一环节缺少证据时，
宁可缩短或省略，也不要编造。

### 影响评估

- 说明修改后由 diff 可以确认的行为、边界或维护性变化。
- 区分直接影响和未改变的范围。
- 不猜测用户规模、性能收益、故障概率或未测量指标。

### 已知问题和限制

- 记录当前 diff 留下且已确认的限制、未覆盖边界或兼容性约束。
- 不把未来计划写成已经实现的内容。
- 没有已知限制时可以省略本节，不要写空泛的“无”。

### 验证或自测结果

- 只写当前会话中有明确命令输出的验证方法和结果。
- 对重要或难复现 Bug，只有存在实际重复验证证据时，才写测试次数和未再复现结论。
- 没有运行测试时，可以写“未运行测试（原因）”，也可以省略验证段。
- 不得伪造“自测通过”“测试通过”或类似结论。

## 正文格式

- 标题与正文之间使用一个空行；标题不得换行。
- 正文使用中文，专有名词、类名、命令和缩写保持规范大小写。
- 正文在约 70 个 ASCII 字符处换行；以中文为主时约 35 个中文字符处换行。
- 不要为了机械满足列宽而拆开路径、URL、命令、类名或其他不可分割标识符。
- 不要让正文行过短或过长；按语义分段，段落之间使用一个空行。
- 多个并列修改优先使用无序列表，避免为插入条目重新编号。
- 小型提交不要为了套模板添加空标题或无信息量段落。

推荐的中大型提交格式：

```text
<type>(<scope>): <subject>

<1～2 行中文变更概述>

问题描述：
- <仅写有证据的现象、条件和影响>

原因分析：
- <仅写已确认的机制>

修改方案：
- <说明真实实现和结构>

影响评估：
- <说明可确认的结果和未改变范围>

已知问题：
- <可选>

验证结果：
- <实际命令和结果，或未运行原因>
```

根据变更类型删除不适用的段落，不要保留空标签。

## 证据纪律

提交说明中的每项声明都必须能在以下至少一种证据中找到依据：

- 所选 diff；
- 当前会话的明确命令结果；
- 用户明确提供且与代码差异一致的事实。

禁止：

- 根据文件名猜测功能已经完成；
- 猜测 Bug 的频率、影响范围、严重程度或根因；
- 声称未运行的测试已经通过；
- 写入所选 diff 没有实现的未来计划；
- 把未暂存或未跟踪内容混入 staged 提交说明。

## 输出

使用以下结构：

```text
依据范围：staged | working tree
混合主题：否 | 是（简述）

建议提交信息：
<type>(<scope>): <subject>

<按需组织的中文正文>
```

输出前再次检查：标题长度和格式正确，正文换行合理，问题、原因、方案、影响和验证均有证据，
并且提交说明只覆盖所选差异。
